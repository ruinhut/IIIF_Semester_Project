# 2. 必要名词

## 2.1 IIIF

IIIF 是 **International Image Interoperability Framework** 的缩写，中文可译为“国际图像互操作框架”。它是一套供图书馆、博物馆和档案馆发布数字图像及相关资料的通用标准。

## 2.2 资源清单文件

IIIF 使用一种称为 **manifest** 的资源清单文件描述一件数字对象。它通常采用 JSON 格式，可能包含：

- 对象标识符；
- 标题和说明；
- 提供机构；
- 日期和地点；
- 版权声明；
- 页面顺序；
- 图像地址。

JSON 是一种结构化文本格式，程序可以直接读取其中的字段。

## 2.3 应用程序接口

API 是 **Application Programming Interface** 的缩写，中文为“应用程序接口”。在本项目中，程序通过接口地址请求数据，服务器返回结构化结果。它通常不需要模拟浏览器点击网页。

## 2.4 变更发现接口和活动流

**Change Discovery API** 在本文中称为“变更发现接口”。它按照 IIIF 标准发布资源的新增、更新或删除信息。

**Activity Stream** 在本文中称为“活动流”。它像一个可以逐页读取的更新清单，程序从中发现资源清单文件的地址。

## 2.5 公共数据模式

**Common schema** 在本文中称为“公共数据模式”。它是团队约定的统一字段和数据结构，使不同来源的数据可以被同一套下游程序读取。

# 4. 项目目标与完成标准

## 4.1 核心目标

1. **提供机构普查：**调查通过 IIIF 发布文化遗产的机构和数据入口，记录数据规模和版权情况；
2. **统一采集：**建立一套能够跨多个提供方发现并取得资源清单文件的程序，尽量避免为每家机构单独编写网络爬虫；
3. **版权筛选：**读取和整理版权声明，只保留符合团队版权规则的记录；
4. **元数据规范化：**把不同来源的数据转换为公共数据模式，至少包括标识符、日期、地点、版权和来源；
5. **数据交付：**交付提供机构清单和一批符合公共数据模式的记录，供 Hafidz 的内容提取程序及 Time Atlas 使用。

## 4.2 项目意义

大量机构都使用 IIIF，因此一套基于共同标准的采集程序可以跨越许多图书馆和博物馆获取数据，而不必反复编写不同程序。

项目完成后：

- 内容提取项目可以从统一入口读取待处理记录；
- 图像项目可以通过同一入口访问不同机构的资源；
- Time Atlas 可以持续接收带有日期、地点和版权信息的文化遗产记录；
- 数据导入可以从一次性的单独脚本转变为可复用、可扩展的流水线。

## 4.3 最低交付成果

- 一份 IIIF 提供机构普查表，包含机构、数据入口、估计规模和版权情况；
- 一条能够实际运行的端到端采集流水线；
- 按版权规则筛选后的资源清单记录；
- 一批符合团队公共数据模式的数据；
- Hafidz 的内容提取程序能够读取的数据文件；
- 为 Time Atlas 接入准备好的日期、地点、版权和来源字段；
- 代码、配置、运行说明、字段说明和已知问题。

# 5. 数据来源和使用顺序

## 5.1 优先使用聚合入口

聚合入口能够一次提供多个机构的数据，因此首先检查：

1. **Europeana（欧洲数字文化遗产平台）：**拥有大规模文化遗产记录，并提供变更发现接口；
2. **IIIF Registry（IIIF 登记目录）：**登记各提供方的活动流，是调查提供机构的主要入口；
3. **Biblissima：**聚合手稿和珍本书等 IIIF 资源。

## 5.2 完整流程跑通后再扩展

- Internet Archive（互联网档案馆）；
- Gallica（法国国家图书馆数字资源平台）；
- Library of Congress（美国国会图书馆）；
- David Rumsey Map Collection（David Rumsey 地图收藏）；
- 其他开放的博物馆、图书馆和档案馆。

# 6. 模块化工作流程

```text
IIIF 登记目录、Europeana 变更发现接口及其他聚合入口
                         ↓
模块一：调查提供机构并登记数据入口
                         ↓
模块二：通过变更发现接口或活动流发现资源
                         ↓
模块三：取得并检查资源清单文件
                         ↓
模块四：识别、统一并筛选版权声明
                         ↓
模块五：提取标识符、日期、地点、版权和来源
                         ↓
模块六：转换并检查团队公共数据模式
                         ↓
模块七：保存、去重、断点续传、记录日志和统计
                         ↓
交付符合公共数据模式的数据
          ↓                              ↓
Hafidz 的内容提取程序              Time Atlas 及其他图像项目
```

## 6.1 模块一：提供机构普查

为每个提供机构建立一条结构化记录，至少考虑：

- 机构名称；
- IIIF 登记目录、活动流或变更发现接口地址；
- 资源类型或馆藏重点；
- 估计记录数量；
- 版权声明的种类和分布；
- 最近检查时间；
- 接口是否正常及异常说明。

输出：提供机构清单，以及数据规模和版权情况统计。

## 6.2 模块二：统一发现

通过 IIIF 的公共机制：

- 读取活动流的当前页面；
- 处理分页并找到下一页；
- 识别新增、更新或删除的资源；
- 取得资源清单文件的地址和来源；
- 尽量让同一套程序跨多个提供方工作。

输出：等待获取和检查的资源清单地址队列。

## 6.3 模块三：获取与基本校验

- 请求资源清单文件；
- 检查请求是否成功；
- 检查返回结果是否为可以解析的 JSON；
- 检查它是否具有基本的 IIIF 结构；
- 保存原始标识符、来源和获取时间；
- 对超时、无效数据和临时网络错误记录明确状态；
- 避免在同一次运行中重复请求同一记录。

输出：可以继续处理的资源清单，以及失败记录和失败原因。

## 6.4 模块四：版权处理

- 读取原始版权声明；
- 将常见版权表达统一为团队规定的类别；
- 按照教师确认的规则保留或排除记录；
- 保存原始版权内容、统一结果和筛选原因；
- 在继续下载图像或交给下游程序前完成版权检查。

输出：通过版权筛选的记录，以及被排除记录的原因统计。

允许哪些版权类别必须由指导教师确认，不能自行假设。

## 6.5 模块五：元数据提取与规范化

公共数据模式至少需要以下五项：

| 中文含义 | 程序字段 | 处理要求 |
|---|---|---|
| 标识符 | `identifier` | 保存对象或资源清单的稳定编号 |
| 日期 | `date` | 同时保存原始日期和能够确定的规范化日期 |
| 地点 | `place` | 同时保存原始地点和能够确定的规范化地点 |
| 版权 | `rights` | 保存原始声明、统一类别及是否允许使用 |
| 来源 | `source` | 保存提供机构、原始资源地址和发现入口 |

不同机构的元数据质量可能相差很大。程序应同时保存原始值和规范化值，遇到缺失或无法判断的内容时明确标记，不能静默删除。

## 6.6 模块六：公共数据模式转换与检查

尽早与 Hafidz、Kaile 和 Ziyi 确认团队的数据格式。本模块负责：

- 将不同来源的字段映射到统一字段；
- 检查必需字段、可选字段、字段类型和缺失值；
- 保存原始来源和处理步骤，保证结果可以追溯；
- 生成 Hafidz 可以直接读取的数据；
- 准备 Time Atlas 需要的日期、地点、版权和来源信息。

## 6.7 模块七：可靠运行与交付

完整流程能够运行后，再补充：

- 去除重复记录；
- 分页和批量处理；
- 中断后从上次进度继续；
- 请求失败后的自动重试；
- 遵守提供方的访问频率限制；
- 保存运行日志和错误清单；
- 统计每个提供方的记录数、通过率和失败率；
- 使用配置文件控制数据源、路径和运行参数；
- 编写本地电脑和实验室服务器的运行说明。

# 7. 开发原则：先完成整条流水线，再逐模块优化

## 7.1 第一阶段：最小可运行版本

第一目标是尽快完成一个规模很小、但每一步都真正运行的版本：

```text
选择一个标准数据入口
→ 发现少量资源清单文件
→ 获取并检查资源清单
→ 读取和筛选版权
→ 提取五个核心字段
→ 转换为公共数据模式
→ 导出 Hafidz 可以读取的小型数据文件
```

争取在第一次正式例会后的两周内完成。初版只支持一个入口和少量记录也没有问题，关键是整条流程已经连通。

## 7.2 第二阶段：分别扩展和优化

初版完成后，再依次改进：

- 增加提供机构和数据规模；
- 完善版权识别和筛选；
- 改善日期和地点等元数据的规范化；
- 增加分页、断点续传、重试、去重和日志；
- 提高公共数据模式的一致性；
- 在实验室服务器上验证较大规模运行；
- 完成与 Hafidz、Kaile 和 Time Atlas 的接口测试。

- 版权原始值、统一类别和是否允许使用；
- 提供机构、资源地址、处理时间等来源追踪信息；
- 数据交付格式及公共数据模式的版本号。

## 10.3 与 Ziyi 和 Time Atlas 的接口

Ziyi 的博士项目研究不经过文字识别、直接搜索 IIIF 图像资源的方法。你需要确认现有代码、提供机构调查资料和接口中有哪些可以复用。

Time Atlas 方面需要确认：

- 接收普通 JSON、逐行 JSON、数据库记录还是接口数据；
- 必须提供哪些日期和地理字段；
- 是否有实验室服务器及访问权限；
- 本地程序如何迁移到服务器；
- 最终交付是一次性数据导入，还是可以持续运行的采集服务。

逐行 JSON 即 JSONL：一个文本文件每行保存一条独立的 JSON 记录，适合批量写入和中断后继续处理。

# 11. 本地电脑与服务器运行

开发初期在个人电脑上用小样本运行完整流程，以便快速调试。程序通过配置文件切换数据源、输出位置、每批数量和运行环境，不能把个人电脑路径直接写死在代码中。

本地版本稳定后，再迁移到导师指定的服务器：

1. 配置 Python 环境、程序依赖和访问凭据；
2. 使用同一个小样本检查本地和服务器结果是否一致；
3. 连接团队存储、公共数据模式或 Time Atlas 接口；
4. 扩大处理规模，检查访问频率、中断恢复、日志和存储；
5. 保存运行配置和程序版本，使结果能够复现。

服务器地址、权限和 Time Atlas 接口尚未在个人说明页中规定，应在项目指导会上确认。

# 12. 第一次项目指导会需要确认的问题

1. 公共数据模式的正式文件在哪里，由谁维护？
2. 哪些版权类别允许使用，哪些需要排除？
3. 第一版从 IIIF 登记目录还是 Europeana 变更发现接口开始？
4. 初版处理多少条记录，使用哪一组固定样本？
5. Hafidz 希望收到什么文件格式，何时进行第一次数据交接？
6. Ziyi 已有的代码、调查数据和服务器中，哪些可以直接使用？
7. Time Atlas 最终需要文件导入、接口连接，还是持续运行的采集服务？

# 13. 一句话总结

你的工作是建立 IIIF 数据流水线的统一入口：**先用一个来源和少量资源清单跑通“发现—获取—版权筛选—提取五个核心字段—转换为公共数据模式—交付下游”的完整流程，再扩展数据来源、规模和可靠性，最终把规范化的文化遗产记录交给 Hafidz 的内容提取程序和 Time Atlas。**
