\begin{center}
{\Large\bfseries 09-23 改进想法：初代流水线后的泛化升级}\\[-0.15em]
Boheng Shang · 2026-09-23
\end{center}
\vspace{-0.4em}

## 一、提出原因

老师认为当前流水线主要处理已知清单中的机构，可能存在泛化能力不足的问题：网络中还有未被 IIIF Registry、官方指南或社区清单收录的 IIIF 内容提供者。

本方案属于**初代确定性流水线完成后的升级工作**，不改变当前优先完成 Module 1--7 的计划。

## 二、Module 1：增加候选提供者发现器

在 Module 1 前或内部增加 **Provider Discovery Scout（提供者发现器）**：

1. 优先读取 IIIF Registry、官方指南、社区清单和项目人工记录；
2. 再通过搜索引擎 API、站点地图和有限网页探索发现可能的新机构及入口；
3. 保存候选机构、候选 URL、来源、发现时间和置信度；
4. 搜索结果仅作为候选线索，由 Module 1 整理、分类和去重，再交给 Module 2 验证。

## 三、Module 3：增加可扩展发现机制

按以下顺序处理入口：

1. **通用标准解析器**：根据 IIIF 的 context、type 和数据结构处理 Change Discovery、Collection、Manifest 和 Image API；
2. **机构适配器库**：复用已经验证的机构 API、分页规则和 Manifest URL 模板；
3. **LLM 辅助分析**：前两种方法失败时，读取机构页面或 API 文档，提出候选入口、接口类型、URL 模板或适配器草案。

LLM 输出不能直接进入正式数据。所有候选方案必须经过 Module 2 网络检查、IIIF 结构校验、有限遍历和自动测试；无法确认的结果进入人工审核。

这里的“学习”指将验证成功的适配规则、证据和测试保存到版本化适配器库中，并非大模型在运行中自动更新参数。

## 四、泛化能力验证

采用未参与开发的机构作为保留测试集，评价：

- 新机构重新发现率；
- 入口类型识别准确率；
- 有效 Manifest 发现量；
- 错误候选比例；
- 专用适配器数量；
- 人工审核工作量。

## 五、实施顺序

\begin{center}
完成初代 Module 1--7
$\rightarrow$ 建立可复现基线
$\rightarrow$ 网络候选发现器
$\rightarrow$ 通用解析器与适配器库
$\rightarrow$ LLM 辅助分析
$\rightarrow$ 保留机构泛化测试
\end{center}
