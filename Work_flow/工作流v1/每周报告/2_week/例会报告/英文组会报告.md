# Timing plan

This report is designed for a twenty-minute supervision slot:

- **12–14 minutes:** prepared progress report;
- **6–8 minutes:** questions, clarification, and decisions with the supervisors.

The nine figures are separate PNG files in the same folder. They should be shown on screen when referenced, but they are deliberately not embedded in this PDF.

# Opening — approximately 45 seconds

Good morning. This week I completed the first end-to-end baseline of the IIIF harvesting pipeline.

The pipeline now starts from a census of IIIF providers, checks all known entry points, discovers Manifest URLs, validates the Manifest structure, applies an automatic rights policy, normalises the metadata, and exports a common object-and-media dataset.

I also added a unified runner, completed the automated tests, and executed the whole pipeline once against all providers currently retained by Module 1.

The main result is that the pipeline works from beginning to end. The main remaining research problem is the generalisation of resource discovery in Module 3.

# What I completed this week — approximately 2 minutes

I completed four connected pieces of work.

First, I revised the handoff between Modules 1, 2, and 3. A provider can have several entry points, so Module 1 now retains all known endpoints. Module 2 checks every endpoint separately. Module 3 groups the checked endpoints by provider and applies several discovery strategies instead of relying on only the first URL.

Second, I completed Modules 4 to 7:

- **Module 4** fetches Manifest JSON, checks the basic IIIF Presentation structure, identifies the IIIF version, and inventories Canvases, image bodies, and Image API services.
- **Module 5** extracts rights evidence and applies a fully automatic policy. Only explicit public-domain or open-license records proceed downstream.
- **Module 6** preserves the raw metadata and normalises the core fields, including identifiers, titles, descriptions, dates, places, languages, types, rights, and provenance.
- **Module 7** maps the data into a provisional common schema, validates it with JSON Schema, verifies object–media links, and exports JSONL and CSV files.

Third, I added a unified runner that executes Modules 1 to 7 in order and records every command, return code, output, and timestamp.

Fourth, I ran the automated test suites. There are **108 tests in total**, and all of them pass when each independently packaged module is tested in its own directory.

# Full live run — approximately 1 minute

The full live run started with **94 providers and 158 candidate endpoints**.

Module 2 checked all 158 endpoints. Module 3 discovered **324 unique Manifest URLs from 10 providers**. Module 4 successfully fetched and validated all 324 discovered Manifests. Module 5 retained **18 Manifests** under the current rights policy. Modules 6 and 7 then produced **18 valid object records and 106 valid media records**, with no rejected output records.

The run took **20 minutes and 45 seconds**, and every module returned successfully.

This was a complete run across all currently selected providers, but it was bounded for responsible testing. Module 3 retained at most 100 Manifests per provider and limited Collection, Change Discovery, and HTML traversal. The result is therefore a reproducible sample and a lower bound, rather than an exhaustive harvest.

# Figure-by-figure explanation — approximately 7 minutes

## Figure 1 — 01_pipeline_throughput.png

Figure 1 shows the pipeline throughput in two panels.

The left panel separates provider and endpoint counts. We start with 94 providers and 158 endpoints. At least one endpoint is reachable for 67 providers, while 10 providers yield at least one Manifest under the current discovery strategies.

The right panel follows Manifest records. Module 3 finds 324 Manifests, and all 324 pass Module 4. The rights policy retains 18. All 18 are then normalised and accepted by the final schema.

**Conclusion:** the technical handoff between modules works, but provider-level discovery and rights availability reduce the final dataset much more than structural validation does.

## Figure 2 — 02_success_and_retention_rates.png

Figure 2 compares the success and retention rates with explicit denominators.

Endpoint HTTP success is 62.66%, and provider reachability is 71.28%. Only 6.38% of providers directly expose parseable JSON at a known entry point. Module 3 currently discovers Manifests for 10.64% of the providers.

After discovery, structural validation, normalisation, and final export all reach 100% for the records entering those stages. Rights retention is 5.56%.

**Conclusion:** the 100% downstream rates show that Modules 4, 6, and 7 are stable on the current inputs. They do not compensate for the lower discovery coverage. The 5.56% rights retention is a policy result, not a software failure rate.

## Figure 3 — 03_module2_endpoint_outcomes.png

Figure 3 gives the Module 2 endpoint outcomes.

There are 92 reachable HTML or other non-JSON responses and 7 directly reachable JSON responses. There are also 29 restricted endpoints, 19 unreachable endpoints, 9 temporary failures, and 2 responses that exceed the configured size limit.

**Conclusion:** an HTML response is not a failed provider. It often means that Module 3 must inspect links or apply another discovery method. Restrictions and temporary failures also need to remain distinct from permanent absence of IIIF resources.

## Figure 4 — 04_module3_discovery_performance.png

Figure 4 is the most important diagnostic figure.

The left side shows 10 successful providers and 84 unresolved providers. The right side shows the Manifest yield for each successful provider. The Bavarian State Library, Carnegie Museum of Art, and Digital Bodleian each reach the configured limit of 100 Manifests. Fragmentarium contributes 18, while six other sources contribute one each.

**Conclusion:** Module 3 can already handle several endpoint types, including Collections, Change Discovery, direct Manifests, HTML-declared links, and explicit links from APIs. However, its provider coverage is still limited. Institutional APIs, search endpoints, identifier enumeration, and Manifest URL templates are the main areas for improvement.

The value 324 should not be interpreted as the total size of these collections, because three providers reached the safety limit and 42 provider runs recorded some form of truncation.

## Figure 5 — 05_module4_resource_inventory.png

Figure 5 uses a logarithmic scale because one Manifest can contain many Canvases.

The 324 valid Manifests contain **54,632 Canvases, 54,652 image bodies, and 54,653 Image API service links**. Module 4 writes 54,654 resource-inventory rows.

**Conclusion:** even a bounded Manifest sample exposes a large quantity of image material. This is enough to test downstream image retrieval and OCR workflows. The 100% Manifest validity means that Module 3 produced high-quality candidates in this run; it does not yet prove support for every possible IIIF extension.

## Figure 6 — 06_module5_rights_statistics.png

Figure 6 shows the automatic rights decision and the detected rights categories.

The policy allows 18 Manifests and excludes 306. The largest category is unknown, with 202 records. There are also 100 non-commercial or otherwise limited records. The allowed set contains 10 public-domain and 8 open-license Manifests.

**Conclusion:** the policy behaves conservatively and automatically, as intended. However, unknown rights are now a major data-retention bottleneck. We need better automatic extraction, inheritance, and conflict handling while keeping the evidence and policy version auditable.

## Figure 7 — 07_module6_field_completeness.png

Figure 7 shows the completeness of the normalised fields in the 18 allowed object records.

Title, description, date, place, and type are present in all 18 records. Language is present in 17. Creator and subject are absent from all 18.

**Conclusion:** all records satisfy the current required core-field rule, but “complete” does not mean that every optional field exists. The present final sample comes from only one provider, so cross-provider metadata normalisation still needs broader evaluation.

## Figure 8 — 08_module7_final_dataset.png

Figure 8 shows the final schema-validation result and the distribution of media records per object.

All 18 object records and all 106 media records pass validation. There are no rejected records. Each object links to between 1 and 52 media records, with a mean of 5.89 and a median of 2.5.

**Conclusion:** the two-table output works: one file contains object-level records and the other contains Canvas or image-level media records joined by record_id. This structure is ready for downstream functional testing. However, every final record in this run comes from Fragmentarium, so provider diversity is not yet sufficient.

## Figure 9 — 09_module_execution_time.png

Figure 9 shows the execution time of every module on a logarithmic scale.

Module 3 takes 804 seconds, Module 4 takes 231 seconds, and Module 2 takes 198 seconds. Module 5 takes 11 seconds. Modules 6 and 7 each take less than one second on the final retained sample.

**Conclusion:** network discovery is both the principal coverage bottleneck and the main performance cost. Checkpointing, caching, resumable pagination, and controlled parallel requests would provide the largest operational improvement.

# Final output and handoff — approximately 1 minute

Module 7 currently exports two linked datasets.

The object dataset contains one record per Manifest. It includes the identifier, title, description, dates, places, language, types, rights evidence, provider provenance, quality information, and the number of linked media records.

The media dataset contains one record per Canvas or image resource. It includes the object record ID, Canvas information, image URL, Image API services, sequence, rights category, and source Manifest URL.

Both datasets are available as authoritative JSONL and inspection-oriented CSV. The dataset manifest records the schema versions, row counts, byte sizes, and SHA-256 hashes.

This gives the next team member two possible inputs:

- 324 structurally valid Manifests and 54,654 resource rows for technical image-access testing;
- 18 rights-approved objects and 106 media rows for a conservative reusable-data workflow.

# Short answers for likely questions

The following notes are for reference during discussion and are not part of the prepared 12–14 minute speech.

**Why do only 10 of 94 providers produce Manifests?**

Many catalogue entries point to institutional websites rather than directly to a Collection, Change Discovery stream, Manifest, or documented API. Some endpoints are restricted or temporarily unavailable. The current generic discovery methods do not yet cover every institutional search API, identifier scheme, or Manifest URL template.

**Does 324 Manifests mean there are only 324 available objects?**

No. Three providers reached the configured limit of 100, and other traversal limits were applied. The 324 records are a bounded reproducible sample.

**Why are only 18 Manifests retained?**

The current automatic policy allows only explicit public-domain or open-license evidence. Most excluded records are unknown or have non-commercial or other limitations. This is a conservative policy decision rather than a parsing failure.

**Can the next student start using the output?**

Yes. The 106 rights-approved media records are suitable for immediate functional testing. The larger 54,654-row resource inventory is also useful for technical testing, but it includes resources that the current rights policy does not allow for downstream reuse.

**What is the biggest technical weakness?**

Module 3 provider coverage. Its current strategies work for several IIIF entry types, but institutional APIs, identifier enumeration, and reusable URL-template adapters need further development.
