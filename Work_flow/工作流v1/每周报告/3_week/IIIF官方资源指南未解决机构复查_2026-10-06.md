# IIIF 官方资源指南未解决机构复查（2026-10-06）

## 1. 复查范围与结论

- 官方索引：<https://iiif.io/guides/finding_resources/>
- 官方指南仓库：<https://github.com/IIIF/guides>
- 本次检查的仓库提交：`c94b51bc335c6050667a536f2ba737807b92f8dc`
- 官方索引有 71 个列表项；排除 `Guide to IIIF personas` 和 `Using the navPlace Extension With Leaflet` 两个教程后，有 69 个资源提供者条目。
- 旧版完整运行在这 69 个条目中只将 5 个标记为 `manifests_found`，将 64 个标记为 `unresolved`。

这 64 个结果不能解释为“机构没有 Manifest”。官方指南已经说明如何从这些机构的单条记录页取得 IIIF 资源。旧结果主要说明程序没有走完官方指南所展示的人工路径，或者没有把人工路径转换成稳定的机器发现方法。

## 2. 旧流水线中确认的问题

### 2.1 Module 1

1. Module 1 导入了全部 69 个官方条目，但多数指南只通过截图说明 Manifest 按钮的位置。旧程序只解析 YAML、Markdown 超链接和明文 URL，无法读取截图所表达的页面操作。
2. Markdown 明文 URL 的正则提取有错误，会把 `](https://...)` 拼进 URL，生成无效重复入口。
3. `endpoint_role` 使用 URL 关键词推断，某些普通网页因为路径包含 `collection` 而被错误标成 IIIF Presentation Collection。

### 2.2 Module 2

1. `403`、限流或临时阻断只说明本次请求受限，不能证明入口不存在。
2. Module 2 即使已经验证出一个 Manifest，也没有把已验证响应可靠交给 Module 3。Digital Commonwealth 的 Leventhal 示例在 Module 2 返回 `200` 和 `sc:Manifest`，但 Module 3 再次请求时遇到 `403`，最终仍被标为 `unresolved`。

### 2.3 Module 3

1. HTML 抓取上限为 3 页、深度为 1，很多运行在进入单条记录页之前就停止。64 个未解决官方条目中有 24 个明确记录了 `truncated: true`。
2. 19 个条目出现过 `403` 或 `restricted`，但旧结果没有把“请求受限”和“未发现 IIIF”严格分开。
3. 达到抓取上限的机构仍被标记为 `unresolved`；正确状态应为 `incomplete_due_to_limit`。
4. 程序会把包含 `iiif` 字样的 CSS、JavaScript 和图标误当成候选，浪费候选数量和网络请求。
5. 程序没有系统处理 Mirador、Universal Viewer、Omeka、机构搜索 API、URL 模板和 IIIF 专用搜索过滤器。

## 3. 建议采用的发现策略

| 代码 | 策略 | 自动化方法 |
|---|---|---|
| `R` | 单条记录页直接链接 | 先枚举记录页，再提取 `href`、`data-*`、JSON-LD、脚本配置和包含 Manifest 的文本。 |
| `V` | Viewer 配置 | 从 Mirador、Universal Viewer 或自定义 Viewer 的初始化配置、查询参数和网络请求中提取 Manifest URL，不自动点击界面。 |
| `T` | URL 模板 | 从一组“记录 URL—Manifest URL”样本中提取稳定变换规则，再逐条请求并验证。 |
| `A` | 目录或搜索 API | 分页枚举记录 ID，将 ID 传给 Manifest 模板；平台 URL 和 JSONPath 放入配置。 |
| `F` | IIIF 过滤搜索 | 使用官方指南提供的 IIIF 过滤结果页枚举记录，再进入 `R`、`V` 或 `T`。 |
| `L` | 旧站或不明确路径 | 先检查当前站点、重定向、归档和新 API，再决定是否能够自动化。 |
| `I` | 只有 Image API | 与 Presentation Manifest 分开记录，不能计入 Manifest 发现成功率。 |

所有候选 Manifest 必须通过以下确定性条件：HTTP 成功、JSON 可解析、声明 IIIF Presentation context、资源类型为 `Manifest`。达到运行预算时输出 `incomplete_due_to_limit`，不能输出 `unresolved`。

## 5. 推荐的实现顺序

1. **修复数据交接**：Module 1 清理 Markdown URL；Module 2 将已验证 Manifest 直接传给 Module 3；Module 3 不再无条件重复请求后丢弃已验证结果。
2. **实现记录页提取器 `R`**：这是官方指南中最常见的模式，应先覆盖直接 Manifest href、JSON-LD、`data-*` 和脚本配置。
3. **实现 Viewer 提取器 `V`**：统一解析 Mirador 和 Universal Viewer 配置、`manifest=` 参数及初始化请求。
4. **实现过滤与枚举器 `F/A`**：先处理 EPFL Omeka S、Digital Commonwealth、Finna、Europeana、Smithsonian 和 Wellcome 等存在明确结构化入口的案例。
5. **实现 URL 模板 `T`**：只从已验证样本中学习模板，每个生成结果仍必须逐条校验。
6. **单独处理 `I/L`**：Image API 不能冒充 Manifest；旧站和迁移站必须记录当前状态与证据。

完成以上修正后重新运行 69 个官方条目。报告必须分别给出：`resolved`、`restricted`、`incomplete_due_to_limit`、`guide_outdated`、`image_api_only` 和真正的 `unresolved_after_complete_strategy`，不能再次把它们合并为一个失败类别。
